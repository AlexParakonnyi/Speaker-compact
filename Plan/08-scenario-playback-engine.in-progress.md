# 08. Движок воспроизведения сценария

**Статус:** in-progress (движок работает, deep sleep — отдельно, план 11)
**Обновлено:** 2026-08-10
**Проект:** device
**Зависит от:** 07, 11 (deep sleep — движок должен уметь работать "поверх" сна между шагами)

## Цель

Пошаговое выполнение активного сценария: ждать нужную задержку (через deep
sleep, см. план 11), проиграть трек с заданной громкостью, перейти к
следующему шагу.

## Детали

1. Состояние выполнения (переживает deep sleep — см. план 11):
   ```c
   RTC_DATA_ATTR bool scenarioActive = false;
   RTC_DATA_ATTR char activeScenarioName[32];
   RTC_DATA_ATTR int currentStepIndex;
   RTC_DATA_ATTR time_t nextEventUnixTime;
   ```
2. Основной цикл (упрощённо):
   - На старте/пробуждении: если `scenarioActive` и сейчас >= `nextEventUnixTime`
     -> выполнить текущий шаг (`startPlayback(steps[currentStepIndex].file)`,
     применить `steps[i].volume` через `speakerWrite()`), иначе — снова уснуть
     до `nextEventUnixTime`.
   - После того как `player.cpp`-плеер сообщает "трек доиграл" — посчитать
     `nextEventUnixTime = now + steps[i+1].delayAfterPrevSec`, `currentStepIndex++`,
     сохранить состояние, уйти в сон (план 11).
   - Если шагов больше нет:
     - `loop == true` (план 07) -> `currentStepIndex = 0`,
       `nextEventUnixTime = now + steps[0].delayAfterPrevSec`, сохранить
       состояние, уйти в сон — сценарий начинается заново без повторного
       `startDelaySec` (та задержка только перед самым первым запуском).
     - `loop == false` -> `scenarioActive = false`. AP не поднимается
       автоматически (см. план 11 — после отыгранного/прерванного сценария
       всегда требуется ручная активация через защёлку) — устройство просто
       остаётся в глубоком сне до щелчка защёлки.
3. Громкость на шаг (`steps[i].volume`) применяется поверх существующего
   `speakerWrite()` из audio_test — переиспользовать как есть, не изобретать
   отдельный путь применения громкости.
4. Активное воспроизведение (пока трек играет) — CPU не спит, это единственное
   время, когда устройство активно потребляет заметный ток помимо
   Wi-Fi-периодов настройки.

## Открытые вопросы

- Что считать источником "текущего времени" для `nextEventUnixTime` — ESP32
  без NTP/RTC-модуля не знает реального времени суток, только относительное
  (`esp_timer`/RTC-счётчик от последнего старта). Скорее всего это не проблема
  (все задержки в сценарии относительные — секунды от активации), но явно
  зафиксировать: устройство не привязано к часам реального времени, только к
  относительным задержкам.

## Критерии готовности

- Сценарий с 2-3 шагами и разными задержками/громкостью проигрывается
  корректно на реальном железе от начала до конца.

## Как реализовано (интерим-версия, БЕЗ deep sleep — согласовано с пользователем)

**Осознанное отступление от черновика плана:** план 08 по своей же шапке
зависит от плана 11 (deep sleep между шагами). Плана 11 ещё нет — самый
рискованный/сложный пункт всего проекта, тестируется только живыми циклами
сна/пробуждения на реальном железе. Обсудили с пользователем 3 варианта
(интерим без сна / сначала план 11 / всё сразу с deep sleep) — выбран
интерим: логика шагов работает **прямо сейчас**, ожидание между шагами —
обычный `millis()`-таймер в `loop()`, CPU и AP остаются активными (не
экономит батарею, это временно). Когда дойдём до плана 11 — заменится
только механизм ожидания (`esp_deep_sleep` + `RTC_DATA_ATTR` вместо
`millis()`), логика шагов (`advanceStep()`, обработка `loop`, применение
громкости на шаг) не меняется.

- Движок — в том же `scenario.h/cpp` (не отдельный модуль), как и
  предполагал `CLAUDE.md` §4.1 ("scenario.h/cpp — модель сценария,
  выполнение, таймеры/RTC").
- `startScenario(name)`/`stopScenario()`/`scenarioTick()` — состояние в
  обычных (не `RTC_DATA_ATTR`) статических переменных модуля: `RTC_DATA_ATTR`
  нужен специально для выживания *deep sleep*, а не для выживания между
  шагами внутри одного цикла бодрствования, так что в интерим-версии не
  нужен (и не переживёт полную потерю питания — но это и не требуется, план
  §6 "Решено": восстановление после потери питания не автоматическое).
- Продвижение шага — `scenarioTick()` смотрит на `currentState`: пока трек
  играет (`waitingForTrackEnd`), ничего не делает; как только
  `player.cpp` сам доиграл трек до `IDLE` — двигает `currentStepIndex`,
  ставит таймер следующего шага. `loop` (план 07) — по окончании шагов
  начинает с шага 0 без повторной `startDelaySec` (только `delayAfterPrevSec`
  первого шага), как и написано в плане.
- Громкость на шаг — через существующий `playbackVolume`/`speakerWrite()`
  (план 08 п.3 явно велит переиспользовать, не изобретать отдельный путь).
  Побочный эффект: это глобальная настройка, после сценария остаётся
  значением последнего шага — осознанно.
- **Активация — временный минимум**, не полноценный план 10 (гашение AP и
  т.д. там ещё нет): добавлены `POST /api/scenarios/activate` `{name}` и
  `POST /api/scenarios/stop`, иначе движок было бы вообще нечем
  протестировать до плана 09/10. `GET /api/status` — добавлены поля
  `scenarioActive`/`activeScenario` для наблюдения за прогрессом.
- **Известное упрощение**: ручной `/api/play`/`/api/stop` во время активного
  сценария не блокируется — `/api/stop` посреди шага заставит движок
  посчитать шаг завершённым и перейти к следующему (т.к. `currentState`
  становится `IDLE`, неотличимо от естественного конца трека). В финальной
  версии (план 09/10) это невозможно в принципе — AP гасится после
  активации, ручных вызовов через API просто не будет. Пока — сценарий и
  ручное управление одновременно "по-честному" не поддерживаются, но и не
  ломают устройство.
- **Обновление:** шаг с пустым `file` — "чистая пауза" (по запросу
  пользователя, план 07) — `scenarioTick()` не вызывает `startPlayback()`,
  сразу переходит к следующему шагу после отсчёта `delayAfterPrevSec`.
- `pio run` — зелёно. **Обновление:** живой тест на реальном железе проведён
  через фронтенд (план 14, теперь готов) — пользователь подтвердил "всё
  работает". Пауза (см. выше) и деталь плана 15 (полноценный экран
  активации с предупреждением про отключение AP) — по-прежнему не сделаны.
