# 06. Загрузка и хранение картинок треков

**Статус:** done
**Обновлено:** 2026-08-10
**Проект:** device + frontend
**Зависит от:** 04

## Цель

Дать возможность прикрепить картинку к треку (из буфера обмена, камеры или
файла на телефоне) с хранением на SD-карте устройства (согласованное решение,
см. `CLAUDE.md` §2.2).

## Детали

### Фронтенд

1. Три источника картинки на плитке трека:
   - **Вставка из буфера обмена** (`paste` event, `ClipboardEvent.clipboardData`)
     — самый быстрый способ на десктопе/при копировании скриншота.
   - **Камера** — `<input type="file" accept="image/*" capture="environment">`
     — на мобильном открывает камеру напрямую.
   - **Файл с устройства** — обычный `<input type="file" accept="image/*">`
     без `capture`, для выбора существующего фото из галереи.
2. **Обязательный ресайз на канвасе перед отправкой** — не отправлять на
   устройство оригинал в полный размер (телефонные фото — по 3-10МБ, SD и
   HTTP-стек ESP32 не должны с этим работать). Целевой размер — по длинной
   стороне ~480-600px, JPEG quality ~80%, через `<canvas>` +
   `toBlob('image/jpeg', 0.8)`.
3. `POST /api/tracks/image` — multipart или raw body с именем файла-трека в
   query/заголовке, картинка после ресайза (десятки КБ, не мегабайты).

### Устройство

1. Хранить картинки на SD в отдельной директории (например `/images/`,
   реальная FAT-директория — тут директории уместны, в отличие от группировки
   треков, картинки физически привязаны к конкретному треку 1:1, не нужен
   индекс). Имя файла картинки = имя трека + `.jpg` (детерминированная связь,
   не нужна отдельная таблица соответствий).
2. `GET /images/<track>.jpg` — раздача статикой через `AsyncWebServer`
   (`server.serveStatic` на директорию, самый простой вариант).
3. Заложить лимит на размер загружаемого файла на уровне HTTP-хендлера (не
   доверять фронтенду, что он всегда ресайзнёт) — отклонять body больше
   разумного порога (например 500КБ) с понятной ошибкой.
4. Учесть в бюджете SD-карты: 16MB flash + отдельная SD-карта для
   треков/картинок (уточнить объём карты, не критично для плана, но стоит
   иметь в виду при расчёте, сколько треков+картинок влезет).

## Открытые вопросы

- Нет — оба конца понятны, decision по хранению уже принят.

## Критерии готовности

- Можно прикрепить картинку всеми тремя способами с мобильного браузера.
- Картинка переживает перезагрузку устройства, отображается в плитке.

## Как реализовано

**Устройство** — отдельный модуль `images.h/cpp` (та же логика разделения
ответственности, что и с `groups.h/cpp`): `storage.cpp` ничего не знает про
картинки, `servers.cpp::processPendingCommands` сводит удаление/переименование
трека с `deleteTrackImage`/`renameTrackImage`, `clear_all` — с `clearAllImages`.

- `IMAGES_DIR` = `/images` — отдельная папка в корне SD (как `TRACKS_DIR`),
  реальная FAT-директория (в отличие от групп — картинка 1:1 с треком, индекс
  не нужен). `imagePath(name)` = `IMAGES_DIR + "/" + name + ".jpg"`
  (конкатенация, не замена расширения — иначе `song.wav`/`song.mp3` делили
  бы один файл).
- `POST /api/tracks/image?file=<track>` — raw body (уже ресайзнутый JPEG),
  тот же `storageBeginWrite/WriteChunk/EndWrite` механизм, что и у
  `/api/upload-audio`. Лимит 500 КБ (`MAX_IMAGE_BYTES`), проверка что трек
  реально существует (`trackExists()` — заодно вынесен как общий хелпер,
  раньше был инлайн-цикл только в `assign_group`).
- `GET /images/<track>.jpg` — `server.serveStatic("/images/", SD, "/images/")`,
  зарегистрирован **до** catch-all `serveStatic("/", SD, "/www/")` — тот же
  урок, что и с `onNotFound` (план 04/17-диагностика): static-handler матчит
  по `startsWith(uri)`, порядок регистрации решает, кто перехватит запрос
  первым.

**Фронтенд**:

- `lib/image.ts::resizeImageToJpeg` — `createImageBitmap` + `<canvas>` →
  `toBlob('image/jpeg', 0.8)`, не больше 600px по длинной стороне, не
  увеличивает изображения меньше лимита.
- `lib/hashColor.ts` — детерминированный цвет по хэшу имени файла для
  заглушки без фото (план 13 п.2).
- `components/TrackImagePicker.tsx` — Dialog с тремя источниками (буфер
  обмена через `navigator.clipboard.read()` + `paste`-событие как fallback,
  камера через `<input capture="environment">`, файл), превью перед
  сохранением, кнопка "Сохранить" — по требованию плана. **Не** bottom
  sheet (`vaul`/`Drawer`) — обычный `Dialog`, тот же осознанный компромисс
  "функционал сейчас, визуал в проходе по плану 12" из предыдущего шага.
- `TrackCard` — картинка (или заглушка: акцентный цвет + иконка ноты) сверху
  карточки, кнопка-камера поверх для смены. Cache-bust через query-параметр
  `?v=<counter>` после успешного сохранения — URL картинки детерминирован
  именем трека, без версии браузер мог бы закешировать старое фото.
- `api/device.ts::uploadTrackImage/trackImageUrl` — добавлены, покрыты
  тестами вместе с `resizeImageToJpeg`, `hashColor`, `TrackImagePicker`.
