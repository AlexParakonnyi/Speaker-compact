# 11. Deep sleep и управление питанием

**Статус:** pending
**Обновлено:** 2026-07-27
**Проект:** device
**Зависит от:** 02 (нужен подтверждённый wake-способный GPIO под кнопку), 08

## ⚠️ Самый рискованный пункт плана технически

Согласованное решение (`CLAUDE.md` §2.4) — настоящий `esp_deep_sleep`, а не
просто "выключить Wi-Fi и держать CPU активным". Это ощутимо сложнее и
требует аккуратной проверки на реальном железе (RTC-память, wake-источники —
классы багов, которые не ловятся на этапе компиляции).

## Цель

Между событиями сценария (план 08) уходить в глубокий сон, просыпаться точно
к следующему событию по RTC-таймеру, либо мгновенно по кнопке.

## Детали

1. **Персистентность состояния между пробуждениями — подтверждено, только
   `RTC_DATA_ATTR`, без дублирования на SD.** Раз при полной потере питания
   сценарий **всегда** требует повторной активации (решение пользователя, не
   автовосстановление) — нет смысла писать прогресс на SD после каждого шага
   (это была бы лишняя нагрузка на карту ради состояния, которое всё равно не
   используется после cold boot). `RTC_DATA_ATTR`-переменные переживают
   обычный цикл deep sleep/wake, чего достаточно.
2. **Обнаружение cold boot** (реальная потеря питания/сброс, не пробуждение
   из сна) — через `esp_reset_reason()` (`ESP_RST_DEEPSLEEP` = было
   пробуждение, доверяем `RTC_DATA_ATTR`; всё остальное — cold boot,
   `scenarioActive` считать `false` независимо от того, что могло остаться в
   RTC-памяти). При cold boot: сценарий не возобновляется, устройство просто
   смотрит на защёлку (план 09) — замкнута -> AP; разомкнута -> нечего
   выполнять, уходит в сон без активного таймера, ждёт щелчка защёлки.
3. **RTC-таймер побудки:**
   `esp_sleep_enable_timer_wakeup((nextEventUnixTime - now) * 1000000ULL)`.
4. **Кнопка-защёлка — wake source:** `esp_sleep_enable_ext0_wakeup(GPIO2, 0)`
   (будим на LOW — защёлка замкнута = переход в AP). GPIO2 выбран как
   RTC-совместимый пин специально под это требование, см. план 02.
5. **Решение "AP или продолжать сценарий" — по фактическому уровню GPIO2, не
   по причине пробуждения** (после того как cold boot уже отсеян шагом 2):
   ```c
   pinMode(LATCH_GPIO, INPUT_PULLUP);
   bool latchClosed = (digitalRead(LATCH_GPIO) == LOW);
   if (latchClosed) { /* поднять AP, план 09 */ }
   else if (scenarioActive) { /* продолжить сценарий, план 08 */ }
   else { /* нечего выполнять — сон без таймера, ждём защёлку */ }
   ```
6. **Опрос защёлки во время активного воспроизведения** (пока CPU не спит,
   `EXT0` не участвует) — проверять `digitalRead(LATCH_GPIO)` периодически в
   цикле плеера (план 08), чтобы щелчок защёлки посреди трека тоже мгновенно
   прерывал сценарий и уводил в AP, а не только между шагами.
7. **Тестирование** — обязательно на реальном железе с амперметром/USB-метром
   мощности, чтобы подтвердить, что deep sleep действительно даёт ожидаемое
   падение потребления (в даташите ESP32-S3 — единицы-десятки µA в глубоком
   сне против десятков-сотен мА активного Wi-Fi/CPU) — включить в план 17.

## Открытые вопросы

- Нет по восстановлению после потери питания — решено (см. п.1-2 выше).
- LED-индикатор (план 02) сделан только под "AP активен" — отдельный
  индикатор "жив и сплю между событиями сценария" не запрошен и не
  закладывается: моргать светодиодом означало бы периодически просыпаться
  специально ради этого, что прямо противоречит цели deep sleep. Если такой
  индикатор всё же нужен — сообщить, тогда пересмотреть compromise
  (например, редкие вспышки раз в несколько минут вместо честного сна).

## Критерии готовности

- Устройство надёжно засыпает и просыпается по таймеру точно к следующему
  событию (проверено на нескольких циклах подряд).
- Пробуждение по кнопке работает независимо от того, сколько осталось до
  таймера.
- Состояние сценария не теряется при обычном цикле сон/пробуждение.
