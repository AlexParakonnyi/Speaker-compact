# 07. Модель данных сценария

**Статус:** done
**Обновлено:** 2026-08-10
**Проект:** device
**Зависит от:** 04, 05

## Цель

Спроектировать и сохранить формат "сценария" — набора треков с индивидуальной
задержкой и громкостью, плюс общая задержка перед стартом всего сценария.

## Детали

1. Предлагаемая схема `/scenarios/<name>.json`:
   ```json
   {
     "name": "Вечерний",
     "startDelaySec": 600,
     "loop": false,
     "steps": [
       { "file": "track1.mp3", "delayAfterPrevSec": 0, "volume": 0.8 },
       { "file": "track2.wav", "delayAfterPrevSec": 30, "volume": 1.0 }
     ]
   }
   ```
   - `startDelaySec` — задержка перед началом сценария целиком (то, что
     пользователь "устанавливает перед активацией" по ТЗ).
   - `delayAfterPrevSec` на каждом шаге — пауза после окончания предыдущего
     трека перед началом этого (для первого шага — пауза после
     `startDelaySec`). Это и есть "задержка на каждый файл" из ТЗ.
   - `volume` на шаг — множитель громкости конкретно для этого трека
     (переиспользует `speakerWrite()`/`playbackVolume`-подобный механизм из
     audio_test, но per-track, не глобальный).
   - **`loop`** (подтверждено) — флажок в интерфейсе редактора сценария
     (план 14), по умолчанию `false`. Если `true` — после последнего шага
     сценарий начинается заново с первого (без повторной `startDelaySec` —
     она только перед самым первым стартом; пауза перед повтором = обычная
     `delayAfterPrevSec` первого шага). Если `false` — доигрывает и уходит в
     режим ожидания реактивации (см. план 11 — не автовосстанавливается,
     нужна ручная активация через AP).
2. API:
   - `GET /api/scenarios` — список сохранённых сценариев.
   - `POST /api/scenarios/save` — создать/обновить.
   - `POST /api/scenarios/delete`.
   - Активация — отдельный пункт (план 10), не часть CRUD.
3. Ограничение на размер сценария (макс. число шагов) — держать в разумных
   пределах (десятки, не тысячи шагов) с учётом ограниченной RAM устройства
   при разборе JSON в память.

## Открытые вопросы

- Схема выше — предложение Claude Code по мотивам ТЗ, детали (`delayAfterPrevSec`
  vs абсолютное время от старта и т.п.) можно скорректировать при первой
  реализации плана 08, если на практике окажется неудобно.

## Критерии готовности

- CRUD сценариев (включая `loop`) работает и переживает перезагрузку.

## Как реализовано

Схема из черновика не менялась (`name`/`startDelaySec`/`loop`/`steps[]` с
`file`/`delayAfterPrevSec`/`volume`) — только данные, без выполнения
(выполнение — план 08, добавится в этот же модуль).

- Новый модуль `device/src/scenario.h/cpp` — один файл на сценарий,
  `/scenarios/<name>.json`, та же изоляция, что у `groups.h/cpp`/`images.h/cpp`
  (не знает про HTTP, не знает про остальные модули). В отличие от групп,
  сценарии **не кэшируются в RAM** — `GET /api/scenarios` читает с SD
  напрямую по запросу (сценариев ожидается немного, в отличие от треков).
  Из-за этого, в отличие от `groups.cpp` (кэш грузится один раз при
  старте), все функции `scenario.cpp` берут `sdMutex` сами — `GET` дергает
  их прямо из контекста AsyncTCP, не через `pendingCmd`.
- `POST /api/scenarios/save` — **JSON-тело, не form-urlencoded** (единственный
  такой эндпоинт в проекте) — `steps` вложенный массив, в form-параметры не
  укладывается. Через `AsyncCallbackJsonWebHandler` из `AsyncJson.h`
  (уже было в `ESPAsyncWebServer-esphome`, не использовалось раньше) с
  буфером 8192Б (дефолт 1024Б мал для полусотни шагов). Требует
  `Content-Type: application/json` от клиента.
- Валидация перед постановкой в `pendingCmd`-очередь: имя сценария (как у
  трека — без `/`/`..`, лимит длины как у групп), лимит `MAX_SCENARIO_STEPS`
  (50), имя файла на каждом шаге (`trackNameSafe`) — но **не** существование
  самого трека (сценарий может ссылаться на ещё не загруженный/уже удалённый
  трек, это нормальное состояние; проверка "трек реально есть" — дело плана
  08 в момент проигрывания, не сохранения).
- `pendingScenario` — глобальная переменная под целую структуру (`pendingArg1`/
  `pendingArg2` — только строки, не хватает для вложенных `steps`), тот же
  принцип очереди из одного элемента.
- `pio run` — зелёно (RAM 18.2%, Flash 28.9%). Живой тест API (`curl`/фронтенд)
  не проводился — фронтенда для сценариев ещё нет (план 14), UI-часть будет
  тестироваться вместе с планом 08.
