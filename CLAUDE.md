# Speaker-compact — контекст проекта

> Этот файл читается автоматически в каждой сессии Claude Code в этом репозитории.
> Обновлять по мере продвижения — см. `Plan/` для детального плана и статуса.

## 1. Что это за проект

Компактное автономное устройство на батарее (ESP32-S3-N16R8), которое проигрывает
аудиофайлы по заранее настроенному сценарию: пользователь через веб-интерфейс
выбирает треки (с превью-прослушиванием прямо из браузера), задаёт задержку и
громкость на каждый, сохраняет это как сценарий, задаёт задержку перед стартом
и активирует. После активации устройство гасит Wi-Fi/точку доступа и уходит в
глубокий сон между событиями сценария, просыпаясь по RTC-таймеру только чтобы
проиграть очередной трек — экономия батареи в приоритете. Чтобы перенастроить
устройство заново, физическая кнопка-защёлка (не momentary — замыкает и держит
контакт до повторного нажатия) прерывает сценарий и поднимает точку доступа снова;
пока AP активна — горит LED-индикатор.

Два независимых проекта в этом репозитории:

- **`device/`** — прошивка ESP32-S3 (PlatformIO, Arduino framework).
- **`frontend/`** — React-приложение для настройки устройства. Собирается в
  статику и **хостится с самого устройства** (SD-карта, тот же AsyncWebServer) —
  никакой зависимости от внешнего хостинга или интернета в поле.

Проект — прямой потомок `PlatformIO/audio_test` (голосовой рекордер на
ESP32-S3): та же плата/экосистема библиотек, но без микрофона — здесь только
воспроизведение по сценарию.

## 2. Ключевые архитектурные решения — согласованы, не обсуждаем заново

Пункты ниже — результат явного согласования с пользователем (см. историю сессии
подготовки плана). Если что-то из этого выглядит спорным — сначала спросить,
почему решили именно так, прежде чем менять.

1. **Фронтенд хостится на самом устройстве.** React собирается в статическую
   сборку, заливается на SD-карту устройства, раздаётся тем же AsyncWebServer,
   что и API. Работает полностью автономно в поле, без интернета. Минус — каждое
   обновление фронта требует пересборки и повторной заливки на SD (см.
   `Plan/16-frontend-device-deployment.md`).

2. **Картинки треков хранятся на SD-карте устройства**, не в браузере. Картинка
   "живёт" вместе с треком независимо от того, с какого браузера/телефона зашли.
   Требует upload-эндпоинт на устройстве и **сжатие/ресайз на стороне браузера
   перед отправкой** (Canvas API, ~400-600px по длинной стороне, JPEG ~80%) —
   ESP32 не должен заниматься декодированием/ресайзом JPEG на лету.

3. **Группировка файлов — через метаданные (`groups.json`)**, не через реальные
   папки на SD. Файл-индекс `имя_файла -> группа`. "Перенос в другую группу" —
   это правка индекса, не перемещение файла на карте.

4. **Энергосбережение — настоящий deep sleep + RTC-таймер между событиями
   сценария**, не просто "выключить Wi-Fi и держать CPU активным". Это самый
   рискованный/сложный пункт плана технически:
   - Между событиями сценария устройство уходит в `esp_deep_sleep`, просыпается
     по RTC-таймеру ровно к следующему событию.
   - Прогресс сценария (текущий шаг, что уже сыграно, когда следующее событие)
     должен переживать каждое пробуждение — RTC-память (`RTC_DATA_ATTR`) как
     быстрый путь, SD-карта как надёжный источник истины на случай полной
     потери питания.
   - Деградация до состояния "живой" аудио-поток на время воспроизведения трека
     (спать нельзя, пока играет звук) — сон только в паузах между треками.
   - Кнопка-защёлка (физически замыкает и держит контакт, не momentary) сидит
     на RTC-GPIO с поддержкой wake (EXT0), чтобы будить устройство мгновенно,
     а не только по таймеру.
   - Режим (AP vs сценарий) определяется **фактическим уровнем GPIO защёлки**
     при каждом старте/пробуждении, не только причиной пробуждения — защёлка
     это стабильное физическое состояние, а не одноразовое событие. Во время
     активного воспроизведения (CPU не спит) — уровень опрашивается
     периодически в цикле плеера, чтобы щелчок защёлки посреди трека тоже
     сразу прерывал сценарий.

5. **Сеть:** точка доступа (AP) поднимается только на время настройки. После
   активации сценария — AP и Wi-Fi гасятся полностью (это же и есть основной
   рычаг энергосбережения наравне с deep sleep). Никакого подключения к
   домашнему Wi-Fi (STA) не предусмотрено — устройство самодостаточно.

## 3. Аппаратная часть

- **Модуль:** ESP32-S3-N16R8 (16MB flash, Octal PSRAM 8MB), несущая плата —
  сторонняя `XH-S3E_V1.2` (не официальный Espressif devkit). **Распиновка
  подтверждена по фото реальной платы** (`device/docs/2026*.jpg`,
  `Plan/02-hardware-schematic-and-pinout.done.md`) — вся шелкография GPIO
  сверена, все выбранные пины (2/8/9/10/11/12/13/15/21/41/47) физически
  присутствуют и вне зарезервированных зон (strapping/PSRAM/USB/UART0).
  `platformio.ini` использует профиль `esp32-s3-devkitc-1` только как
  источник дефолтных пинов тулчейна — `board_build.flash_size = 16MB`
  выставлен отдельно под реальный флеш.
- **Это прототип — прошивается через внешний USB-UART программатор**, не
  через штатный USB (нативный USB на GPIO19/20 не задействован и остаётся
  просто в резерве). Вход в bootloader/выход в рабочий режим — вручную через
  `EN`/`IO0` (GPIO0), без авто-reset схемы. Подробная процедура и питание —
  `device/docs/wiring.md` (раздел "Программатор").
- **Усилитель — подтверждён: тот же MAX98357A**, что и в audio_test (I2S,
  9dB gain по умолчанию, пины DIN/LRC/BCLK переиспользованы 1:1 — GPIO41/47/21).
- **Кнопка — механическая защёлка** (замыкает и держит контакт до повторного
  нажатия, не momentary), на RTC-совместимом GPIO2 для deep sleep wake.
- **LED-индикатор** точки доступа — GPIO15, горит пока активен AP.
- **SD-карта — обычный SPI-брейкаут** (`TF Micro SD Card Module`, фото в
  `device/docs/`), не SDIO-модуль — поэтому прошивка использует `SD.h`+`SPI.h`
  (GPIO10/11/12/13), не `SD_MMC` (см. `device/docs/wiring.md`). Это изменение
  относительно первой версии плана, где закладывался `SD_MMC` 1-бит.
- **Измерение заряда батареи — ADS1115** (4-канальный 16-бит I2C АЦП,
  компактный модуль V/G/S/D + 4 канала, фото в `device/docs/`), на I2C-шине
  GPIO8 (SDA)/GPIO9 (SCL) — дефолтные I2C-пины для `esp32-s3-devkitc-1`.
  Опциональное расширение — **TCA9548A** (I2C-мультиплексор, 8 каналов), если
  понадобится больше устройств на шине; не требует дополнительных GPIO (сидит
  на той же паре SDA/SCL). Firmware-часть (чтение напряжения, конвертация в
  % заряда) — ещё не реализована, это новый пункт плана, пинаут зарезервирован.
- **Батарея/питание/BMS (схема заряда, защита) — по-прежнему вне зоны
  ответственности этого плана.** Пользователь явно попросил не беспокоиться об
  этом — проектирует отдельно. **Уточнение:** это касается именно силовой
  части (заряд/защита); чтение уровня заряда через ADS1115 — уже в зоне
  ответственности прошивки (см. выше), это разные вещи.

## 4. Лучшие практики из предыдущих проектов (обязательны к соблюдению)

Ниже — то, что реально сработало (или наоборот, стоило дорого) в `audio_test`,
`Rover-Camera`, `Rover-Brain`. Не изобретать заново, переиспользовать паттерны.

### 4.1. Структура файлов (как в Rover-Brain/Rover-Camera)

Один модуль — пара `.h`/`.cpp`, назван по зоне ответственности, не по слою
абстракции. Проверено на audio_test при переносе с монолитного `main.cpp`:

- `global.h` — общее состояние (`extern`), доступное всем модулям.
- `storage.h/cpp` — SD, файлы, WAV-заголовки, список треков (`trackList`,
  `TRACKS_DIR`).
- `groups.h/cpp` — группы треков через `/groups.json` в корне SD (план 05):
  `groupList`/`trackGroups` в памяти, `loadGroups()`/`saveGroups()`. Не знает
  про HTTP и про `storage.cpp` — при удалении/переименовании трека вызывающая
  сторона (`servers.cpp::processPendingCommands`) сама сводит оба модуля.
- `speaker.h/cpp` — весь I2S TX: инициализация, `speakerWrite()` (громкость +
  насыщение int16 в одном месте, не дублировать по местам использования).
- `player.h/cpp` — state machine воспроизведения (переименован из `recorder.h/cpp`
  audio_test — в этом проекте записи нет, только воспроизведение: по сценарию
  и превью из браузера).
- `scenario.h/cpp` — модель сценария, выполнение, таймеры/RTC.
- `power.h/cpp` — deep sleep, wake-логика (в т.ч. опрос защёлки), сохранение/
  восстановление состояния.
- `servers.h/cpp` — весь HTTP API + раздача фронтенда, именно так называть файл
  (не `web.h`/`api.h`) — конвенция из Rover-проектов.
- `main.cpp` — только `setup()`/`loop()`, тонкий оркестратор, вызывает `initXxx()`
  из каждого модуля. Не должен содержать бизнес-логику.

### 4.2. Многозадачность и общие ресурсы

- Хардварный I/O (I2S, будущие датчики) — в отдельной FreeRTOS-задаче
  (`xTaskCreatePinnedToCore`, ядро 0 — там же WiFi/TCP стек, ядро 1 — `loop()`),
  а не внутри `loop()`. Причина: в audio_test чтение микрофона внутри `loop()`
  конкурировало по времени с обработкой HTTP-команд и heartbeat-логами — звук
  был неровным. Перенос в отдельную задачу с `vTaskDelayUntil` решил проблему.
- Общий хардварный ресурс (файл на SD, буфер кадра камеры) между задачами —
  оборачивать `SemaphoreHandle_t`/мьютексом. Паттерн `frameSemaphore` из
  Rover-Camera и `micMutex` из audio_test — бери за образец.
- **Все мутирующие операции с SD_MMC/File — строго из одного места** (не из
  HTTP-хендлеров напрямую — `AsyncWebServer` выполняет их в отдельной задаче
  `AsyncTCP`, конкурентный доступ к файлу реально портил звук в audio_test).
  Два паттерна, в зависимости от формы операции:
  - Короткие атомарные команды (play/stop/delete/rename) — HTTP-хендлер
    выставляет команду в очередь (`pendingCmd`), выполняет её `loop()`.
  - Потоковая многочанковая запись (upload аудио, деплой фронтенда — план 16) —
    так в очередь не положишь одной командой, поэтому свой `sdMutex`
    (`global.h`), которым обёрнуты и `storageBeginWrite/WriteChunk/EndWrite`
    в AsyncTCP-хендлере, и файловые операции плеера в `loop()`.

### 4.3. Библиотеки и сборка

- WebSocket/HTTP — `AsyncTCP-esphome` + `esphome/ESPAsyncWebServer-esphome` —
  по опыту пользователя стабильно работают на ESP32, без глюков WebSocket.
  Не переключаться на другой форк без явной причины.
- После **любого** изменения кода — реальная сборка `pio run`, не полагаться на
  память о том, что "должно скомпилироваться". IntelliSense в VSCode может
  показывать ложные ошибки (не переиндексировался путь) — ориентир только
  фактический билд.
- Перед использованием любого стороннего API/структуры — проверять реальные
  установленные заголовочники (`find`/`grep` по `.pio/libdeps` или
  `~/.platformio/lib`), а не полагаться на память о библиотеке. Так нашли, что
  `ESP32-audioI2S`, кроме класса `Audio` (который сам владеет I2S), содержит
  автономные функции декодера (`MP3Decode`/`AACDecode`), которые можно
  прогонять через свой собственный `speakerWrite()`.
- Встроенный в прошивку JS (если понадобится PROGMEM-страница где-то ещё) —
  проверять синтаксис отдельно: извлечь блок `<script>` и прогнать
  `node --check`, C++-компилятор ошибки в JS не ловит.

### 4.4. Железо — типовые грабли на ESP32-S3

- **Общая земля обязательна** между каждым внешним модулем (мик, усилитель,
  датчики) и платой. Отсутствие GND было причиной целой сессии отладки в
  audio_test (постоянный нескоррелированный шум, выглядело как программный баг).
  Проверять мультиметром (прозвонка GND-GND, не только VDD-GND на самом модуле).
- Зарезервированные GPIO на ESP32-S3, не трогать без явной причины: strapping
  (0, 3, 45, 46), Octal PSRAM (33-37 — актуально для N16R8/N8R8), native USB
  (19, 20), плюс то, что уже занято под SD_MMC/дисплей/кнопки на конкретной плате.
- `SD_MMC` на ESP32-S3 не имеет пинов по умолчанию (в отличие от классического
  ESP32) — обязателен явный `SD_MMC.setPins()` до `begin()`.
- Перед тем как полагаться на распиновку — свериться с реальными фото платы
  (не с généric pinout-картинкой из интернета), если фото есть в `docs/`.
- MEMS/I2S-микрофоны и другие модули с "загадочным шумом вместо сигнала" —
  диагностировать методично: дамп сырых сэмплов, потом график
  (waveform+спектрограмма) вместо перебора настроек протокола вслепую. В
  audio_test именно график (не перебор I2S-форматов) быстро показал, что дело
  в отсутствии GND, а не в конфигурации.

### 4.5. Безопасность

**Сохранять безопасность и писать код с учётом недопущения взломов — как
устройства, так и фронтенд-части.** Явная инструкция пользователя, применять
при любых доработках API/прошивки/фронтенда, не только при первой реализации.
Контекст: устройство раздаёт AP с паролем и принимает HTTP-запросы напрямую
от браузера, без прокси/бэкенда — сервер на устройстве обязан
самостоятельно валидировать всё, фронтенд ему не доверенный клиент.

Чек-лист ниже — сверяться при **каждой** новой фиче, трогающей
соответствующую часть, не только при первой реализации. Финальная сверка
всей системы целиком (не по частям, а на стыках между ними) — отдельным
пунктом плана `20-security-audit` в самом конце (см. §9).

#### 4.5.1. Device — HTTP API (`servers.cpp`)

- [ ] Любой новый эндпоинт с именем файла/путём в параметрах — валидировать
  до использования: `trackNameSafe()` для треков (запрещает `/` и `..` в
  имени), `pathSafe()` + проверка префикса `/www/` для деплоя фронтенда. Не
  убирать при рефакторинге, переносить в новые эндпоинты.
- [ ] Новый мутирующий эндпоинт — через `pendingCmd`-очередь (короткие
  атомарные команды) или через `sdMutex` (потоковая запись), не трогать SD
  напрямую из HTTP-хендлера AsyncTCP (см. §4.2).
- [ ] Приём файла с фронтенда — лимит размера (`MAX_UPLOAD_BYTES`), whitelist
  расширений (`audioExtensionAllowed()`), проверка свободного места на SD
  (`SD.totalBytes() - SD.usedBytes()`) до начала записи — см. пример в
  `handleAudioUploadBody`.
- [ ] Ответы об ошибках — без утечки лишних внутренних деталей (структура
  путей на карте и т.п.) сверх того, что нужно для диагностики с фронтенда.

#### 4.5.2. Device — SD-хранилище (`storage.cpp`)

- [ ] Треки — только в `TRACKS_DIR` (`/tracks/`), никогда не в корне SD и не
  в `/www/` (фронтенд).
- [ ] Массовые операции (`clear_all` и любые будущие аналоги) — работать
  строго по заранее вычисленному списку (`trackList`), не рекурсивным
  обходом произвольной директории — никакого "удалить всё в X" без явного
  ограничения на тип/расширение файла.
- [ ] Новые категории файлов на SD (`groups.json`, данные сценария — план
  05/07) — держать вне `TRACKS_DIR`, чтобы `clear_all`/upload треков их не
  задевали ни при каких условиях.

#### 4.5.3. Device — сеть/AP (`network.cpp`)

- [ ] API работает только пока поднята точка доступа (см. §2 п.5) — никаких
  внешних callback/telemetry/OTA-эндпоинтов без явного отдельного запроса
  пользователя.
- [ ] Пароль AP — сейчас осознанно фиксированная строка в коде (см.
  `Plan/09`), это принятый компромисс "просто" vs "безопасно"; не путать с
  секретами вроде реальных Wi-Fi-паролей домашней сети (их тут нет, AP — свой)
  и не откатывать это решение без обсуждения.
- [ ] Новый функционал не должен требовать интернета или соединения с
  внешними серверами — устройство самодостаточно (см. §2 п.5).

#### 4.5.4. Frontend (`frontend/src`)

- [ ] Данные с устройства (имена файлов, группы, метаданные сценария) —
  рендерить как текст, не через `dangerouslySetInnerHTML`. React экранирует
  JSX по умолчанию — не обходить это ради удобства.
- [ ] Не считать, что запрос к API устройства мог прийти только из штатного
  UI — фронтенд-валидация (например форм) — это UX/быстрая обратная связь,
  а не единственная линия защиты; финальная проверка — на устройстве (см.
  §4.5.1).
- [ ] `scripts/deploy.js` и любые другие локальные dev-скрипты, обращающиеся
  к API устройства напрямую — не логировать и не коммитить пароль/IP, если
  они станут чем-то большим, чем "свой AP на столе".

#### 4.5.5. Секреты (весь репозиторий)

- [ ] `.gitignore` в корне покрывает `.env*`, `*.pem`, `*.key`, `secrets.*`,

### 4.6. Логирование в прошивке (ESP_LOGx — обязательно, не Serial)

**Любой новый или изменяемый `.cpp` файл прошивки** — использовать `ESP_LOGx`, не `Serial.print*`.
Это уже применено во всех текущих модулях (Plan/18), новый код должен продолжать тот же стиль.

```cpp
#include <esp_log.h>
static const char* TAG = "module_name";  // имя = имя файла без расширения

ESP_LOGI(TAG, "Playback started: %s", filename.c_str());   // INFO — штатный ход
ESP_LOGW(TAG, "SD mount retry %d", attempt);               // WARN — что-то не идеально
ESP_LOGE(TAG, "SD.open failed: %s", path.c_str());         // ERROR — реальный сбой
```

Правила:
- `\n` в конце — **не добавлять**, ESP_LOGx сам добавляет.
- `Arduino::String` → всегда `.c_str()` в качестве `%s`-аргумента.
- `Serial.begin(115200)` в `main.cpp` — оставлять: нужен для USB-CDC baud rate.
- Уровень (`CORE_DEBUG_LEVEL=3`) задан в `platformio.ini`; для релиза без логов — поменять на `0`.
- После изменения кода — запускать `pio run` (или через PlatformIO в VSCode), не полагаться
  на IntelliSense: он может не подхватить новые `#include`.

### 4.7. Тесты фронтенда (Vitest + React Testing Library — обязательны для новых компонентов)

Инфраструктура уже настроена (Plan/19). **Любая новая функция или компонент** — должны
сопровождаться тестом, написанным в той же сессии, что и код.

**Запуск:**
```bash
cd frontend
npm run test:run   # однократный прогон (CI / перед деплоем)
npm test           # watch-режим (оставить открытым во время разработки)
npm run test:ui    # браузерный UI с живым деревом тестов (нужен @vitest/ui)
```

**Структура файлов:**
- Тест — рядом с тестируемым кодом: `Foo.tsx` → `Foo.test.tsx`
- Общий setup: `src/test/setup.ts` (уже содержит jest-dom матчеры)
- Вспомогательные хелперы (render с провайдерами и т.д.) — `src/test/utils.ts`

**Стиль тестов:**
```tsx
import { describe, it, expect } from 'vitest'
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { MyComponent } from './MyComponent'

describe('<MyComponent />', () => {
  it('показывает заголовок после загрузки', async () => {
    render(<MyComponent />)
    expect(screen.getByRole('heading', { name: /трек/i })).toBeInTheDocument()
  })
})
```

- Запросы — через accessible roles (`getByRole`, `getByLabelText`), не CSS-классы.
- Взаимодействие — `userEvent` (не `fireEvent`): он правильно имитирует реальный браузер.
- Тест проверяет поведение с точки зрения пользователя, не детали реализации.

## 6. Решено (для справки, чтобы не переспрашивать)

- Загрузка аудио — с фронтенда, `POST /api/upload-audio` (не только через
  SD-картридер). API файлового CRUD — плоские роуты (`/api/play`,
  `/api/stop`, `/api/delete`, `/api/rename`, `/api/clear_all`,
  `/api/upload-audio`), не `/api/tracks/*` — так уже было реализовано и
  закоммичено, решили не переименовывать (план 04).
- Сценарий может зацикливаться — флажок `loop` в редакторе (план 07/14),
  выключен по умолчанию, включается пользователем осознанно.
- AP защищена паролем (не открытая сеть) — см. план 09 за вариантами, откуда
  берётся пароль.
- Восстановление после потери питания — **не автоматическое**, сценарий
  всегда требует повторной активации через AP. Отсюда следствие: состояние
  сценария хранится только в `RTC_DATA_ATTR` (переживает deep sleep), не
  дублируется на SD (план 11) — меньше сложности и износа карты.
- Автотаймаут отключения AP при бездействии — **не нужен**, кнопки-защёлки
  достаточно как явного контроля пользователя (план 09).
- Заливка фронтенда на устройство — **через HTTP-эндпоинт**
  (`POST /api/deploy-frontend`), не вручную через картридер, и делается
  **рано** (план 16, сразу после bootstrap) ради удобства итераций при
  разработке — см. §9 "Порядок выполнения".

## 8. Родственный проект — Level-compact

Пользователь указал на `C:\VS_code_proects\Level-compact` как на проект с
"похожим модулем" — реально проанализировано, полезное ниже. **Важный
нюанс: там классический ESP32 (`board = esp32dev`), не ESP32-S3** — поэтому
номера пинов оттуда **не переносятся** напрямую в Speaker-compact (разные
strapping/PSRAM/зарезервированные зоны у ESP32 и ESP32-S3). Переносится
**принцип** — "использовать пины по умолчанию для своего чипа" (у
`Level-compact` I2C на GPIO21/22, дефолт для classic ESP32; у Speaker-compact
I2C на GPIO8/9, дефолт для `esp32-s3-devkitc-1` — разные числа, тот же
принцип), архитектурные паттерны и особенно фронтенд-стек — не конкретные GPIO.

Что подтверждено/взято:

- **Фронтенд-стек подтверждён боевым использованием**: `Level-compact/front/`
  уже на React + Tailwind + полный набор shadcn/ui-компонентов (accordion,
  dialog, drawer, sheet, slider, switch, tabs, toast, tooltip и т.д. — почти
  всё, что нужно и Speaker-compact). Это не просто хорошая идея — это уже
  проверенный пользователем стек. При реализации плана 03/12 — взять
  `Level-compact/front/src/components/ui/*` как стартовую точку вместо
  установки shadcn с нуля.
- **`data/` с готовой React-сборкой** в `Level-device/` подтверждает паттерн
  "фронтенд хостится с устройства" — но там через `LittleFS` +
  `pio run -t uploadfs` (USB-заливка). Speaker-compact делает то же самое
  через SD + свой HTTP-эндпоинт (план 16) — так как нужна заливка по Wi-Fi
  без кабеля, `uploadfs` для этого не подходит.
- **У `Level-compact` вообще нет SD-карты** (`board_build.filesystem =
  littlefs` — фронтенд и данные во внутренней flash) — распиновку SD-модуля
  Speaker-compact оттуда взять было неоткуда; она определена независимо, по
  реально купленному модулю (SPI-брейкаут) и дефолтным SPI-пинам
  `esp32-s3-devkitc-1`, см. `device/docs/wiring.md`.
- **Веб-стек другой**: `Level-compact` использует синхронный `WebServer.h` +
  `links2004/WebSockets`, не `ESPAsyncWebServer`. Speaker-compact сознательно
  остаётся на `AsyncTCP-esphome`/`ESPAsyncWebServer-esphome` (см. §4.3) —
  не переключаемся без причины, это просто к сведению как альтернатива.
- **`BatteryMonitor.h/cpp`** (INA219, I2C, с программным детектором зарядки
  по тренду напряжения) — референс на будущее, но **другая микросхема**:
  Speaker-compact измеряет батарею через **ADS1115** (4-канальный АЦП), не
  INA219 — INA219 меряет ток/напряжение/мощность по шунту, ADS1115 просто
  читает напряжение с делителя на одном из каналов. Логика детекции заряда по
  тренду напряжения из `BatteryMonitor.cpp` всё ещё может пригодиться как
  референс алгоритма (не кода — интерфейс к чипу другой).

## 9. Порядок выполнения (актуальнее, чем номера файлов в Plan/)

   код уже может использовать предложенные пины).

   перед `06`/`07`, `07` перед `08`, и т.д.).
6. **Последним шагом, когда все остальные пункты закрыты** — `20`, итоговый
   аудит безопасности всей системы (не по одной фиче, а по проекту целиком,

   финальная сверка перед тем, как считать проект завершённым.
